# Handoff — 2026-08-31 mac

## 목적과 상태

이 handoff는 mac 환경에서 decision card, 경쟁제품 적용성 문맥, full-split 평가, 법령 RAG
설계를 진행한 뒤의 재개 지점이다. Git 작업 트리는 이 handoff 커밋 직전까지 clean이어야
하며, raw competition data와 `outputs/`는 Git ignore 상태다. 다른 환경에서는 artifact
archive와 원본 `data/raw/`를 함께 복원한다.

## 오늘 완료한 일

### 1. Decision card와 제품문맥

- v1/v2 decision card를 versioned artifact로 만들었다.
  - 생성: `python scripts/build_decision_cards.py --version v1|v2`
  - v2는 v10~v18에 대회 제공 경쟁제품 CSV의 적용성 원칙을 card text로 추가한다.

### 3. 법령 RAG 사전 설계

법령패키지 전체는 Gemma tokenizer 기준 약 1,210,403 tokens라 통째로 넣을 수 없다. 조문 번호가
명시된 법률·시행령·시행규칙만 우선 추출한 합집합도 14,262 tokens이며, 이는 예규의 장/절과
별표를 제외한 하한값이다. 현 full-split v2 system prompt는 약 4,259 tokens이고 prompt
budget은 30,268 tokens다.

따라서 법령은 item table의 명시 참조를 key로 쓰는 deterministic lookup으로 설계한다.
법률·시행령·시행규칙은 조문 전체, 예규/지침은 장/절 전체, 별표는 별표 전체를 fixed context로
넣고 공고문만 split한다. 법령을 문자 수로 자르거나 유사도 검색으로 파일을 추정하지 않는다.

약칭→실제 파일→selector 및 reference-overlap 중심 group 초안은 아래 문서에 있다.

- `docs/legal_reference_mapping.md`

핵심 예시: 항목표 v23의 `지방계약법시행령 제35조`는 이전 코드에 등록돼 있던 별칭이 아니다.
원문을 직접 대조해 `지방자치단체를 당사자로 하는 계약에 관한 법률 시행령.txt`의
`제35조(입찰공고의 시기)`로 확인했다. v23에는 추가로
`지방자치단체 입찰시 낙찰자 결정기준.txt`의 제7장 제3절이 필요하다.

### 4. Group 호출 수와 조기 종료 분석

법령 bundle을 group별로 다르게 주려면 group은 실제 LLM 호출 단위가 되어야 한다. 이전에
“group은 실행 단위가 아니다”라고 설명한 것은 잘못이었고, 바로잡았다.

EXP-014 dev-200은 총 376 document pass(공고당 평균 1.88회; 1회 67건, 2회 90건, 3회 43건)였다.
reference-overlap 초안의 12 group을 모두 실행하면 4,512 호출이다. pass별 저장 judgment를
이용해 아래의 안전한 조기 종료를 시뮬레이션했다.

- non-absence item: 첫 1에서 최종 1 확정
- absence-AND item: 첫 0에서 최종 0 확정
- 한 group의 모든 active item이 확정돼야 다음 문서 호출 생략

결과는 4,512→4,315 호출, **197회(4.4%) 절감**이었다. v20 단독 group은 376→204로 크게
줄었지만, v6~v8 group은 376→376이었다. 따라서 조기 종료는 반드시 구현할 최적화이지만,
12-way group 호출의 비용 문제를 해결할 정도는 아니다. 이 수치는 기존 24-item prompt의
pass judgment를 group prompt에 투영한 구조적 시뮬레이션이지, 법령 RAG 성능 예측은 아니다.

## 중요 주의사항

1. root `config.yaml`과 `submission/runtime_config.json`은 현재 `context_strategy: single`,
   decision card/product context 없음이다. EXP-014는 별도 historical config다. 따라서
   “현재 최적 실험”과 “현재 canonical 제출 정책”은 일치하지 않는다. RAG를 넣기 전에 final
   policy를 명시적으로 다시 확정하고 두 config를 함께 바꿔야 한다.
2. `full_split_merge`의 non-absence positive는 대상 source-document fragment의 변경 없는
   evidence substring이 있어야 한다. absence items(v10, v11, v16, v18, v20)는 AND 결합이며
   같은 evidence gate를 적용하면 안 된다.
3. 법령 selector가 불명확한 v20, v21은 추측하지 않는다. `docs/legal_reference_mapping.md`의
   `?`를 원문에서 확인한 후에만 derived map에 넣는다.
4. 법령 group은 reference overlap을 우선으로 작성했으나, 최종 group은 각 완성 bundle의 실제
   Gemma chat-token 길이를 측정한 뒤 확정한다. 12개가 곧 최종 제출 호출 수라는 뜻은 아니다.

## 다음 권장 단계

1. `docs/legal_reference_mapping.md`의 `?` selector 및 예규 heading boundary를 원문에서 검증한다.
2. 검증된 map을 `data/derived/legal_reference_map_v1.json`으로 생성하고 source hash, selector,
   chunk hash, exact Gemma token count manifest를 함께 만든다.
3. group별 fixed legal bundle token profile을 먼저 낸다. 이 단계에서는 LLM 호출을 하지 않는다.
4. 그 결과를 바탕으로 shared pipeline에 `active_items`, group별 prompt/reference, 결과 병합,
   그리고 item terminal-state 기반 조기 종료를 한 번에 설계한다. 실험과 submission은 반드시
   같은 pipeline을 사용한다.
5. first-20에서 현재 EXP-014와 법령 RAG group policy를 비교한 뒤 full dev-200으로 확대한다.
